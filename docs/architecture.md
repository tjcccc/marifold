# Architecture

marifold is a local-first, single-owner personal AI workspace: one person runs it on their own devices with their own provider credentials. This document is the project layer of the owner's `architecture-principles.md`: runtime pieces, package responsibilities and limits, dependency directions, trust boundaries, terms, and decisions. `AGENTS.md` holds the working rules; `DEVLOG.md` the dated history.

## Runtime pieces

- **CLI process** (`marifold …`): one-shot commands, `marifold agent`, and the TUI. Bare `marifold` loads the ESM TUI through a dynamic `import()` and runs it in the same process, either against a local `MarifoldRuntime` or against the local service as a remote runtime.
- **Service process** (`marifold service`): the Fastify API, the static Web UI, the scheduler, the Telegram bridge, the run registry, and the workspace manager and executor. It binds to loopback by default; non-loopback binds accept only private-network peers.
- **Web UI** (browser): a static React app served by the service; it reaches everything over the service HTTP/SSE API.
- **Workspace bridge** (`apps/bridge`, deployed separately as a Cloudflare Worker with one Durable Object, or as a Node server): relays end-to-end encrypted messages between the devices of one workspace, with SQLite state. It authenticates members and never sees message contents.
- **Device job workers**: detached Node processes that run approved full-access and `sudo_exec` shell jobs and record their results on disk, so jobs survive disconnects and service restarts.
- **Providers**: model APIs (Ollama, OpenAI-compatible, Anthropic, ChatGPT, xAI, Copilot) reached through `@priest-ai/core`.

## Packages

Each package is imported only through its `src/index.ts` entry point.

- `packages/core` (`@marifold/core`): runtime, config, profiles, memory, sessions, the agent subsystem, runs, schedules, Skills and SkillApps, and the device-hosted workspace protocol implementation. Must not depend on any other marifold package except `workspace-protocol`, and must not format output for a renderer.
- `packages/service` (`@marifold/service`): HTTP transport over core: security filtering, request validation, route modules (`RunRoutes`, `SessionRoutes`, `ConfigRoutes`, `ProfileRoutes`, `SkillAppRoutes`, `ChatRoutes`, `TaskRoutes`, `WorkspaceRoutes`, `AgentComputerRoutes`), SSE, and error mapping (`ServiceErrors`). Must not hold business rules beyond request validation and response sanitizing.
- `packages/client` (`@marifold/client`): the typed HTTP/SSE client shared by the TUI, CLI, and Web UI: requests with the session-owner header, SSE parsing, resumable `followRunEvents`, session lease routes and the renewal loop that terminal and browser clients share, workspace startup selection, and composer token helpers. Must not depend on core at runtime.
- `packages/tui` (`@marifold/tui`): the Ink terminal renderer of the `AgentEvent` contract, local or service-connected. Must not contain model-side logic.
- `packages/cli` (`marifold`): command parsing and terminal output; launches the TUI and the service.
- `packages/workspace-protocol` (`@marifold/workspace-protocol`): wire types, limits, identities, signing, membership certificates, and encryption shared by core and the bridge. Must stay free of runtime and transport code.
- `apps/web` (`@marifold/web`): the browser renderer. Imports `@marifold/core` only for types, only in `src/api/types.ts`.
- `apps/bridge` (`@marifold/bridge`): the relay server. `src/relay` is the platform-neutral, synchronous relay (routing, authentication, revocation, delivery) over a small SQLite port; `src/node` (Node `http` + `ws` + `node:sqlite`) and `src/cloudflare` (Worker + Durable Object, bundled by esbuild into `dist/cloudflare/worker.js`) are thin adapters. Depends only on `workspace-protocol`.
- `@priest-ai/core` (external, `../priest-typescript`): model-side primitives.

`@priest-ai/core` remains marifold-agnostic. marifold depends on it; it does not know about marifold. Since 2.4 it carries the model-side agent primitives — native tool-call transport, the `runWithTools` loop helper, structured stream events, cancellation, and image input. In 2.8 it also owns the OpenAI Responses transport, provider-neutral reasoning configuration, safe reasoning summaries, opaque continuation, and cached/reasoning token accounting. marifold owns concrete tools, approval policy, task state, and rendering. Priest owns talking to models; marifold owns acting on the world.

## Dependency directions

```text
packages/cli  -> packages/tui -> packages/client
packages/cli  -> packages/service -> packages/core -> packages/workspace-protocol
packages/tui  -> packages/core (local runtime and types)
packages/core -> @priest-ai/core -> providers
apps/web      -> packages/client (runtime); packages/core (types only)
apps/bridge   -> packages/workspace-protocol
packages/cli  -> apps/bridge (build-time only: staged for `marifold workspace bridge install` and `deploy cloudflare`)
```

Enforcement: package manifests (pnpm resolves only declared dependencies), Biome `noImportCycles`, a `noRestrictedImports` override for `apps/web`, and the file-size ratchet in `pnpm lint`. `packages/core` has no dependency on the service, TUI, CLI, client, Web UI, or bridge.

## Trust boundaries

- **HTTP service edge** (`packages/service/src/Security.ts`, `Validation.ts`): the direct peer and `Host` header are filtered to loopback or private networks; an optional bearer token and a CORS allowlist apply. Route modules validate bodies and queries before calling core. Raw provider keys never leave the process; host file paths in system errors are shown only to local clients.
- **Workspace bridge** (`apps/bridge`, `packages/core/src/workspace`): devices authenticate with membership certificates signed by the pinned host identity; messages are end-to-end encrypted, so the relay sees only routing headers. Forwarded API requests pass `workspaceApiPath`, and host-only settings (providers, service, credentials, and agent computer lifecycle and settings, checked by the sending device in `AgentComputerRoutes`) are refused with 403. Paired devices must run the same release.
- **Agent tools** (`packages/core/src/agent`): every effect goes through `ApprovalPolicy` and per-run `RunWorkspace` capability roots. Paths are assessed at their real destination (symlinks resolved); shell runs inside the platform sandbox in its own process group, with no unrestricted fallback; scoped shell is routine (no prompt unless the shell mode is `deny`) because the sandbox, not a prompt, sets its limits; a scoped call may name one extra in-home `write_folder`, which escalates like a file write outside trusted folders (once, for the run, or trust) and is re-validated (`runGrantFolder`, `coversProtectedRoot`) before it joins that call's write roots. `FilePolicy` classifies file-tool paths the same way on every device: reads follow the read mode; ordinary writes inside home are routine (no prompt unless writes are denied) and overwrites and deletions go to the Trash; sensitive account paths (`SENSITIVE_HOME_ENTRIES`) ask for reads, which a profile may allow per root (`sensitive_read_grants`, never for `~/.marifold`), and writes there, outside home, or to login/startup configuration ask for each call.
- **Model, tool, and remote output**: treated as untrusted. CLI output strips terminal control sequences, the TUI drops device-control strings from every frame, and the Web UI renders Markdown without raw HTML.
- **SkillApp templates** (`packages/core/src/app`): statically compiled; read permissions are declared, resolved to real paths, and refused for Marifold private state and sensitive account data. A selected profile Skill's `reads:` files pass the same `HostReadGrants` check before joining a SkillApp run's exact-file grants.
- **Agent computer** (`packages/core/src/computer`): one Docker container on an internal network, driven with `docker exec` argument arrays; no bind mounts (only a named `/home` volume), socket, privilege, or Marifold credentials inside. Its only exit is `EgressProxy`, which refuses local and private destinations. Files enter only through `computer_put`, which follows the device's read approvals and refuses credential stores and Marifold state. See `docs/agent-computer.md`.
- **Device execution** (`DeviceExecution`, `DeviceExecutionWorker`): full access is a local opt-in per device; `sudo` passwords travel encrypted for one use and are never stored; durable jobs are scoped to the workspace that started them.

## Core subsystems

The runtime layer is thin. `MarifoldRuntime` resolves config/profile/session settings and selects profile memory with the current prompt. `ChatTurns` runs ask/stream chat turns through `PriestEngine`, including the bounded web search/read tool loop and memory control payloads; `ProviderEngines` builds those engines and their request config (provider adapters, OAuth credential refresh, reasoning options). `MarifoldRuntime.createAgentRunner()` wires the agent subsystem over the same engine factory, TaskStore, and config policy, and `SkillAppOperations` runs SkillApp operations through those engines or an isolated read-only Agent run.

The agent subsystem lives in `packages/core/src/agent`:

- `AgentRunner` optionally plans, iterates through the approval-aware tool loop, and records the final outcome, emitting a renderer-agnostic `AgentEvent` AsyncGenerator. Observable checks use the same tools inside the loop; there is no separate model-authored self-grade. The CLI, TUI, Web UI, and service consume this event contract, so it stays free of renderer formatting. The deprecated `verification` variant remains accepted only for compatibility with pre-v0.24.2 producers and is not emitted by the current runner.
- `ToolRegistry` holds effectful `AgentTool` implementations (`inspect_attachment`, `read_attachment`, `search_attachment`, `read_file`, `write_file`, isolated `shell_exec`, per-run `python_package_install`, and depth-1 `ask_profile`) plus the interaction-only `ask_user` tool. Opaque attachment IDs resolve through a format-neutral local resource boundary: inspection returns metadata, capabilities, a read-only run path, and at most an 8k-character preview; later reads and searches return bounded derived views. Complete-file work uses local programs against the staged original instead of serializing it through model context. Effectful tools may flag risky calls (`assessRisk`), which forces approval; `ask_user` instead emits a bounded, validated question request and waits for one complete submission without entering the permission system.
- `RunWorkspace` creates a private capability set under `~/.marifold/runs/<run-id>/`: internal runtime-home state, staged read-only attachments, work/output/temp/cache, and `.venv`. Upload names are sanitized, local/embedded images are copied into `input/`, and the agent sees an ID/name/type/size manifest rather than eagerly receiving every attachment. Browser-readable documents are staged without duplicating their extracted content into the Agent objective. Individual tool results are capped at 24k characters and the accumulated turn-local tool exchange at 64k; older results become short replay-safe placeholders. Regular output files produce renderer-neutral `artifact` events, while download resolution rechecks containment and rejects symlinks. The Web renderer recognizes model-authored `sandbox:` Markdown only when the target maps exactly to an artifact published by the same run; it never opens the host path itself. User-facing `~`/`$HOME` retain normal account-home semantics. The shell sandbox reads the home like `read_file` but denies the sensitive roots (`sensitiveHostRoots`: credential stores, browser profiles, `~/.marifold` apart from the run's own directories), checked at the real path so symlinks cannot reach them; writes stay limited to cwd, trusted folders and the run directories, because sandbox writes get no Trash copy. Installer and package-tool sandboxes narrow reads to explicit roots (plus uv's managed Python install). The active profile and configured global skill directories are added as narrow read-only roots when they resolve inside the user's home; they never become write roots, and external configured paths remain approval-gated. Shell execution goes through `ScopedProcess`; macOS uses Seatbelt and unsupported platforms fail closed instead of falling back to the host. Shell network is denied, filesystem writes are allowlisted, global runtime/package directories stay read-only, and common host-control channels (unrelated signals, Apple Events, clipboard, Launch Services mutation, keychain IPC) are denied.
- `python_package_install` is the only network-enabled process path. It accepts registry requirement names only, invokes `uv` into the per-run `.venv`, always requires one-time approval, and mounts only disposable environment directories so package build hooks cannot read user inputs or a selected repository.
- `ApprovalPolicy` maps tool kinds (`read`, `write`, `shell`, `network`, `delegate`) to `allow`/`ask`/`deny` from the optional `[agent]` config section. `ask` requires the caller-supplied `ApprovalHandler`; unattended runs degrade `ask` to deny.
- Agent guidance treats tentative ideas and discussion as conversation, without starting filesystem investigation from earlier tasks. Denied calls return guidance to stop seeking that access. Identical tool/argument retries are denied without another approval prompt for the remainder of the run; independent authorized work can continue, and a new run can request approval again.
- Tool calling is native-first through `@priest-ai/core` 3.x. Provider-executed tools are separate from caller-executed tools: OpenAI/ChatGPT/xAI and verified Bailian Responses models receive hosted `web_search`, while supported Bailian Chat Completions models receive `enable_search`; Marifold suppresses its duplicate fallback function and preserves unrelated file/shell/interaction tools. Responses and Anthropic caller-tool loops carry opaque reasoning continuation back to the same provider while exposing only safe summary text to marifold renderers. In `auto` mode, a provider that rejects caller tools switches the run to control-block mode: prompt-embedded `<tool_call>` blocks parsed with the same pattern as the memory control blocks, so the loop works on small local models too.
- Images from earlier turns of the same session stay reachable: a non-lean run lists up to four of them (from turns before the current or edited one) as `earlier-image-N` IDs, and `inspect_attachment` loads, optimizes, and stages one only when the model asks. Uploading an image is the user's grant to inspect it within its conversation; a moved or deleted source file is reported as unavailable.
- Ordinary agent runs use profile memory like chat: selected memory is recalled into context with the memory policy, and when a run completes its hidden `<memory_save>`/`<memory_forget>` blocks (stripped from visible output) and the prompt's explicit statements update the profile (the prompt fallback skips facts the model saved that turn). Skills (lean runs), runs given memory by their caller, and profiles with memories off neither recall nor write. Failed runs write nothing; task state is never promoted into profile memory.
- Interactive agent sessions persist one clean user→assistant pair per append-only run. The prompt is saved when the run starts (so a new session exists, and can be retried, before any answer) and the outcome when it ends. Successful runs store the final answer; failed or cancelled runs store a concise terminal outcome so submitted prompts survive resume without exposing raw tool-loop framing. Failed historical regenerations do not replace the prior successful exchange. A prompt left without an answer (the service stopped mid-run) gains one when regenerated, if it is the newest.

Chat resolves search in three states: provider/model-hosted search when the verified transport supports it, Marifold's `WebSearchTool` fallback when `[web_search].enabled`, or an explicit unavailable instruction when neither exists. Bailian's auto matrix is deliberately conservative, with per-provider `responses`/`chat`/`off` overrides for new or exceptional models. Hosted search does not enter Marifold's caller tool loop or emit its per-call approval events; the effective agent `network` policy can disable it, and unattended runs require explicit network `allow`. Search remains model-initiated from natural-language requests. Ollama local inference never receives network access; its model calls Marifold's fallback function, which performs the external request through the selected DuckDuckGo, Firecrawl, or account-backed Ollama Cloud backend. Fallback `web_search`/`read_file` exchanges remain turn-local — sessions store only the prompt and final answer, and memory payloads apply only from the final response.

Scheduling lives in `packages/core/src/schedule`: a file-backed `ScheduleStore` (cron via `croner`) and a minute-resolution `Scheduler` hosted inside the `marifold service` process. Scheduled firings are unattended agent runs (`AgentRunOptions.unattended`): `[agent.unattended]` approval overrides apply, and `ask` degrades to deny. Schedule results link to TaskStore tasks tagged `scheduled`.

The App subsystem (`packages/core/src/app`) statically compiles restricted `marifold.skillapp.v1`/`.v2` `<apps_dir>/<name>/skillapp.ts` templates into renderer-neutral definitions. A v1 operation binds service-owned string state to one app-local Skill, one explicit provider/model, and one normalized result; it remains profile-free and tool-free. A v2 operation instead registers an existing profile, resolves one Skill through its profile-over-global catalog, loads the live profile documents, and inherits or locally overrides its model. An operation may select among a statically allowlisted set of those Skills from service-owned form state; every candidate is validated before the App loads. Selected Skill bundles are mounted through the existing narrow read-only run workspace. Static `FileAccess`/`FolderAccess` declarations add fail-closed read-only capabilities without serializing host paths to clients; exact files do not widen to their parent directories. `AttachmentState` uploads retain only metadata in instance snapshots and stage original bytes behind the existing opaque attachment inspection boundary for the selected operation. Optional memory is read-only and optional history is confined to the ephemeral App instance/profile reference; neither touches profile conversation history. Profile Agent permissions and trusted folders are not inherited, and write/shell/network/delegation tools are not exposed. Ephemeral instances implement read-only output bindings, button runs as exclusive cancellable executions (polled by renderers, with a blocking compatibility route), and debounced latest-wins state triggers. The catalog reports bundles that fail to load alongside valid definitions. The TypeScript authoring file is never imported or executed. The Web UI renders the normalized semantic component tree at bookmarkable `/apps/<app-name>` paths, and a future SwiftUI client can consume the same service data. Approval-aware effectful actions and general scripted App logic remain out of scope.

The skill subsystem (`packages/core/src/skill`) defines the `marifold.skill.v0` primitive — a prompt template with declared `{{variables}}` and an optional run mode. `SkillStore` loads user skills from `[paths].skills_dir` (default `~/.marifold/skills`) and each profile's `skills/` directory, with profile skills shadowing global ones; `parseSkill`/`renderSkillPrompt` validate and expand them. A separate compiled built-in registry contributes protected `$skill-installer` and `$skill-creator` definitions to effective listing/resolution without materializing them in either mutable directory; their names are reserved. Their agent-mode instructions use the approval-aware `manage_skill` tool, which defaults user-facing mutations to the global catalog, validates local sources/content and bundled text paths through `SkillStore`, and mutates exactly one explicit scope. An explicit `--profile <name>` is checked against the stored profile catalog before the tool resolves that profile's skill directory. The TUI invokes an indexed skill directly with core's binding rules; service/Web clients use `resolveSkillInvocation` to do the same over HTTP. Both paths resolve exactly one skill before model execution, inject its expanded body and bundled-file directory, preserve the typed invocation in durable history, and use history-isolated execution so one prompt skill cannot inherit another prompt skill's style. A Skill is also the shared unit a graphical SkillApp consumes: v1 binds semantic form state to an app-local Skill and explicit model, while v2 binds it to an installed profile Skill and that profile's live context/model resolution. See `docs/tui.md`.

The TUI (`packages/tui`, Ink/React) is the primary interactive surface and a pure renderer of `AgentRunner.run`→`AgentEvent`; it is agent-only: prompts and `$skill` runs (including skills that declare chat mode) all use the agent; `/btw` side questions use one tool-less `ask` call that is never saved. The TUI adds no model-side logic. It is an ESM-only package the CommonJS CLI loads through a dynamic `import()` (kept a real import via a `new Function` escape hatch so `tsc`'s CommonJS emit does not turn it into a `require()`). Logic lives in pure, unit-tested modules under `src/core/` (input grammar, event→view mapping, an `appState` reducer, command/skill registries); Ink components under `src/ui/` stay thin, and the `App` controller composes `useRuns` (agent runs, steering, cancel), `useApprovals` (approval and question prompts, session grants), and `useSkills` (`$skill` binding and runs). Steering (`AgentRunOptions.steering`) drains text typed during a run between iterations. Approval UX (allow-once / session-grant / persist-to-config / deny) reuses the core `ApprovalPolicy`; non-persistable risks expose only allow-once/deny, while the process sandbox enforces the hard filesystem and network ceiling independently of approval. Optional `ask_user` events open a separate keyboard question modal, batch every answer, and resume through `AgentRunOptions.userInputHandler`.

The Web UI (`apps/web`, Vite + React 19) is the second interactive surface and a pure renderer of the service API — it holds no model-side logic and reaches core only through HTTP (its wire types are `import type`-only re-exports from `@marifold/core`, funneled through one file). It mirrors the TUI's thin-components/fat-testable-core split: `api/` (fetch + SSE + the resumable `followRun` loop), `state/` (a pure `threadReducer` grouping runs into cards — the web analogue of the TUI's `applyAgentEvent` — plus a `RunFollowers` manager), `lib/` (markdown/format/permissions/clean-path routing), with React confined to `components/` and `screens/`. Ordinary messages always start agent runs, whose live cards hold plans, folding tool rows, optional batched question sheets, the separate approval sheet, steering pills, cancel, and catch-up replay after reloads. The retained one-shot chat stream supports explicitly chat-mode Skills and compatibility clients without exposing a mode switch. Telegram likewise routes ordinary messages through the Agent path. The shell keeps named service connections: the built-in same-origin server plus validated remote HTTP(S) roots with independent bearer tokens. Switching servers remounts data-owning screens and namespaces last routes and drafts by server so stale profiles, sessions, and live requests cannot cross that boundary. Production builds stage the browser bundle inside `@marifold/service`, so the single public `marifold` install hosts it same-origin by default; `[service].web_dir` / `--web-dir` overrides that bundle. Static routes retain their traversal guard and extensionless SPA fallback; bearer auth is scoped to `/v1/*` so the shell stays reachable, and an Origin equal to the request's allowed Host passes the origin policy. In development the Vite dev server binds to `127.0.0.1` and talks to the service cross-origin via `--cors-origin http://127.0.0.1:5173`.

Config, profile, model, provider, and session commands are local management surfaces. Config export/import copies local config, profile files, memories, and optional sessions; it does not introduce cloud sync. These commands do not introduce agent tools or web/app runtimes.

The service API is local-first and defaults to loopback. It exposes health/status, sanitized config/provider/model data, profiles, memories, sessions, ask/chat, SSE streaming chat, task-state CRUD/event routes, read-only schedules, and — since v0.35.0 — live agent-run routes: `POST /v1/runs` starts a run through core's `RunRegistry` (`packages/core/src/runs`), `GET /v1/runs/:id/events` streams the `AgentEvent` union over resumable SSE (sequence ids, `Last-Event-ID` replay, heartbeats), and clarification/approval/steer/cancel POSTs drive it mid-flight. The registry holds the live layer TaskStore cannot (abort handle, pending clarification/approval resolution, steering queue, event buffer). Clarifications validate all answers against the exact pending request and never grant capabilities; approval semantics (once/always/trust/deny with profile persistence and timeout auto-deny) remain distinct. Security is one `onRequest` hook: unconditional direct-peer private-source filtering for every non-loopback bind, bind-scope/DNS-rebinding Host validation, an exact-match CORS origin allowlist (`[service].cors_origins`), and optional bearer-token auth (`[service].token_env`) that never widens network reachability. The service-hosted Web UI is same-origin at each scope. The CLI owns single-instance process management under `~/.marifold/service/`: both foreground entry points claim the same state, daemon start detaches the built CLI with inherited environment and file-backed output, `status` reads live state and an optional bounded log tail, `stop` sends the same graceful SIGTERM path, and `restart` gracefully replaces the service in the same mode using persisted safe launch metadata. Legacy public launch state remains readable only to warn the owner and is discarded on restart. The metadata records only the token source or environment-variable name, never a raw bearer token; raw-token restarts require the caller to supply it again. Service lifecycle remains bounded: SIGINT/SIGTERM closes Fastify and its runtime owners before explicit process termination, a second signal or five-second timeout forces connection closure, and listen failures run the same ownership cleanup. The wire contract is documented in [service-api.md](service-api.md); the AgentEvent union serialized verbatim is that contract. Still absent by design: WebSocket sync and multi-user access.

Model validation checks local configuration and provider model-list endpoints where available. It does not delete, pull, or mutate local provider storage.

Profiles are loaded from lightweight directories:

```text
profiles/default/
  INSTRUCTIONS.md
  profile.toml
  memories/
    user.jsonl
    preferences.jsonl
    auto_short.jsonl
```

`INSTRUCTIONS.md` is the sole canonical human-authored instruction document. Marifold maps it through its Priest `ProfileLoader`; Priest does not depend on the Markdown filename. When the canonical file is absent, the resolver combines legacy `RULES.md`, `PROFILE.md`, and `CUSTOM.md` content in that existing effective order without mutating disk. `marifold doctor --fix` owns the explicit, backed-up migration.

marifold owns the profile memory file meaning and passes selected memory to `@priest-ai/core` through `PriestRequest.memory`. The memory path can be disabled per profile through `profile.toml` or per run through `--no-memories`. When enabled, marifold injects memory policy instructions, strips hidden `<memory_save>` and `<memory_forget>` blocks from visible output and saved session history, applies JSONL mutations after the turn, applies conservative prompt fallback extraction, applies prompt-driven forgets, and trims low-priority short-term memory.

Structured memory is stored in JSONL under profile directories. The current memory subsystem is integrated inside `packages/core/src/memory`, but it is intentionally package-shaped: schema, persistence, selection, prompt/control extraction, and policy remain separated enough to extract into a future `@marifold/memory` package once agent/task memory requirements settle.

Memory is context, not authority. Human-authored profile instructions and the current user message outrank memory. Recall includes priority `0..3`, and simple greetings include only priority `0` memories; Deep does not change recall.

Deep is one global switch (`default.deep`); a request, SkillApp model, or SkillApp profile reference may override it, and profiles cannot. `config/DeepReasoning` maps it per provider (medium when on, low when off, never high) and `config/ReasoningRetry` wraps every adapter to retry once without the setting when a model rejects it. It does not change context assembly, memory recall, or agent behavior.

SQLite session continuity is reused from `@priest-ai/core`. marifold-owned metadata stays in companion tables in that same database: `marifold_session_display` holds session title/pin/archive state, `marifold_profile_display` holds profile pin state, `marifold_turn_attachments` holds display-only image sources, and `marifold_response_metrics` holds content-free timing/model/token/cost metadata for completed chat and agent exchanges. Response metrics use the stable zero-based user-turn ordinal rather than Priest's rewritten SQLite turn ids; session rename, edit, truncate, clear, and delete operations maintain the companion rows. Profile contact previews and activity dates are derived from the latest durable session/assistant turn rather than copied into profile files or model context. Removing a stored profile clears its profile-display row but deliberately retains its session turns and response metrics.

Task state is stored as JSON files under `paths.tasks_dir`, defaulting to `~/.marifold/tasks`. Task state is generated working context: objective, status, plan, events, summary, next action, profile, and session references. It is separate from durable profile memory and is not promoted into profile memory by default.

### Device-hosted workspaces

`packages/core/src/workspace` turns one device into the host of a workspace that the owner's other devices join. `WorkspaceManager` owns pairing, invitations, revocation, and per-workspace `BridgePeer` connections (`workspace/bridge`); `WorkspaceStore` persists identities, memberships, and an idempotent request journal beside the config. The host routes runs to an execution device through `WorkspaceRuns`; a guest that enabled execution runs host-requested tools in `WorkspaceExecutor`, which builds its own capabilities and accepts only short-lived, call-specific grants. `DeviceDelegateTool` and `WorkspaceDevicesTool` let a host conversation delegate to a guest. Sessions are reserved per client through `SessionLeases` (shared with local TUI processes through a lease file); a running task holds its session until it ends, and `takeover` moves a session between the owner's clients. See `docs/workspaces.md` and `docs/device-execution.md`.

### Agent computer

`packages/core/src/projects` holds Projects (see [projects.md](projects.md)). `ProjectStore` keeps projects, their rosters with a Lead, and session links in the sessions database (`marifold_projects`, `marifold_project_members`, and `marifold_project_sessions` from `sessions/ProjectSessionsTable`, which also records each session's floor). Sessions keep Priest's `profile_name` (the profile a session started with); a link row makes it a project session, which any session listing without a `projectId`, `latest`, per-profile `clear`, and the contact-list preview (`sessions/ProfileActivityQuery`) skip. Session rename and delete carry or remove the link. Deleting a project keeps its sessions as ordinary ones. Profile rename moves rosters, Leads and floors in the same transaction as sessions; deleting a profile that leads a project is refused. `agent/Mentions` is the one `@` parser (`@name`, `@"name"`, ending at punctuation, a possessive, CJK text or a path, ignored in code and e-mail addresses), used for device mentions now and profile mentions in project sessions next. A profile may not take a workspace device's name or id, and a device may not join under a host profile's name, so a mention is never ambiguous; the check needs the service's device list, so profiles created by a CLI or local TUI without a running service are not checked.

`packages/core/src/computer` gives the agent one Linux container with an account per profile that has access. `AgentComputer` owns settings, Docker detection, the container lifecycle (image, internal network, egress container, `/home` volume), and profile access; `AgentComputerAccounts` reconciles the accounts by stable UID (the default profile is the fixed `marifold` account); `AgentComputerFiles` runs commands and moves files with `docker exec`; `ComputerTools` exposes `computer_exec`, `computer_write_file`, `computer_put`, and `computer_get` to profiles with access; `EgressFilter`/`EgressProxy` are dependency-free so they can be copied into the image. The service exposes it at `/v1/agent-computer`; other workspace devices may read its status and give or remove profile access, nothing else. See `docs/agent-computer.md`.

## Glossary

- **Profile**: a named identity with instructions, settings, memory, and Skills. Not a workspace.
- **Session**: a persisted conversation, owned by one profile.
- **Run**: one agent execution, streamed as `AgentEvent`s and tracked by `RunRegistry`; it may produce artifacts.
- **Task**: ephemeral working state of a run (`TaskStore`), never promoted into memory.
- **Skill**: a `marifold.skill.v0` prompt template invoked as `$name`.
- **SkillApp**: a statically compiled `skillapp.ts` template that binds form state to Skills.
- **Workspace**: a device-hosted space shared by the owner's devices. **Host**: the device that owns its data and credentials. **Guest**: a joined device. **Bridge**: the relay between them. **Executor**: a guest's opt-in tool execution for host runs. **Executor-only member**: a guest paired with `access: "executor"` in its host-signed membership; it answers execution requests and may only report status or leave.
- **Lease**: an app's reservation of an open session (owner = device + app: every browser/tab on a service's Web UI shares it, its terminals share theirs, and a workspace device going through the bridge is its own device); **takeover** moves it to another app or device.
- **Attachment**: a user-supplied file staged read-only for a run. **Artifact**: a file a run produced in its output directory.
- **Agent computer**: the agent's own Linux container, with an account per profile that has access, driven by Marifold on the host with no approval prompts inside, isolated from the user's devices and network.
- **Trusted folder**: a profile folder (never root or sensitive account data) added to the shell sandbox's writable roots, stored home-relative (`~/…`) so it applies on every device; file tools no longer need it inside home. The entry `~` is not a folder capability: it lets sandboxed scripts create and modify files in home without unlink/rename.
- **Routine file work**: a file-tool call inside home that is not sensitive or startup configuration; approved without a prompt unless the kind is `deny`, including on guests and in unattended runs.
- **Sensitive read grant**: a home-relative sensitive root (e.g. `~/.ssh`) a profile may read without asking, stored as `agent.sensitive_read_grants`; it never widens shell or write access.
- **Scoped / full access**: sandboxed shell inside run capabilities, versus an approved account-level job on the device.

## Decisions

- 2026-06-12: `@priest-ai/core` owns talking to models; marifold owns acting on the world (tools, approval, task state, rendering).
- 2026-06: one load-bearing TypeScript implementation; the TUI is Ink/React loaded by the CommonJS CLI through a dynamic `import()`.
- 2026-08: the service stays single-owner: no multi-tenant accounts, credential pooling, or public-internet exposure (`AGENTS.md`).
- 2026-09: workspaces are device-hosted with a relay bridge; a cloud-hosted workspace was rejected as too large.
- 2026-10-08: a running task holds its session lease until it ends, so a client that leaves cannot lose the finished turn; 2026-10-09: the owner can take a session over from another client; 2026-10-10: lease owners are derived by the service as device + app (a reload or another tab of the same app is not "in use", matching Claude Code's terminals), and a cross-process run claim keeps two runs out of one session.
- 2026-10-13: the agent computer is a Docker container driven by the host with `docker exec`, not an OrbStack machine paired as a workspace device: an isolated OrbStack machine still reached the Mac's LAN address, and driving it from the host keeps every key outside the computer and keeps runs (and their approvals for the user's devices) on the host.
- 2026-10-13: one agent computer with an account per profile, not one container per profile: profiles are faces of one agent, so they share one machine and software; the default profile is the `marifold` account. New profile names must be valid Linux usernames so the account name is the profile name. Accounts are tidiness, not isolation (all have `sudo`).
- 2026-10-13: workspace members are full by default; an executor-only invitation pairs a device that can only execute (for headless machines whose key untrusted software could read). The host enforces it from its own device record on every bridge operation, deny by default; the membership format stays version 1 with an optional `access` field.
- 2026-10-13: a workspace belongs to one person, so other devices may reach Marifold state, but the rule follows the sending device: its own local request has no hard block on `~/.marifold` (approval each time), while a request from another workspace device gets default deny with a readable allowlist (`profiles`, `skills`, `apps`, `schedules`, `tasks`, `prompts`, `runs` and their configured paths; approval each time, never writable), because `config.toml`, workspace keys and the sessions database hold credentials and self-escalation paths. The agent computer is shared the same way: other full members see it and give or remove profile access; its lifecycle and settings stay with the host. Both are decided from the bridge-authenticated sender, not the client.
- 2026-10-13: Think is a global switch rather than a per-profile setting, because profiles are faces of one agent and the effort level is a property of the request, not the persona. It asks for medium or low effort, never high, because marifold is not a coding agent. Effort fields are verified only for the providers in use (ChatGPT, xAI, Bailian, Ollama, plus Anthropic and Copilot); a one-time retry covers models that reject them instead of a per-model capability table.
- 2026-10-14: Think was renamed Deep with no alias, because low and medium both reason; the switch sets depth, not whether the model thinks. `marifold doctor --fix` renames `[default].think` and SkillApp `think:` options; `/think` and the SkillApp compiler say it was renamed. The sessions database keeps its `think` metrics column.
- 2026-10-24: the bridge is one relay instance with SQLite state; Redis and the Vercel adapter were removed. A personal bridge needs no horizontal scaling, and SQLite runs both in a Cloudflare Durable Object (free plan, no server) and next to a Node process. Frames delivered to an online device are held in memory until acknowledged (up to five seconds) and stored only otherwise, which keeps Durable Object writes near zero; a pending hold timer also keeps the object from hibernating. Each device chooses its own bridge proxy per workspace connection, with no `HTTPS_PROXY` fallback.
- 2026-10-26: file permissions treat every workspace device as the owner's own: a guest returns its real risk assessment and the requesting profile's policy decides (the guest's own `deny` and hard blocks still win), instead of every guest call asking once with no persistent option. Routine home file work needs no prompt because overwrites and deletions are undoable through the Trash; dedicated `make_directory`, `move_path` and `trash_path` keep ordinary file organization out of full-access shell, which stays per-call. Trusted folders still never cross the bridge; sensitive read grants are home-relative so one grant applies on every device.
- 2026-10-26: scoped `shell_exec` (Python scripts included) runs without a prompt and reads the home except sensitive roots, matching `read_file`; it keeps no network and narrow writes. Before this, each scoped command asked once and the sandbox could not read ordinary home files (or uv's Python), so the agent escalated routine data processing to full access. Full access stays per-call and is never a fallback for a failed scoped command. Python is not trusted as a language; the sandbox boundary is what makes it routine.
- 2026-10-26: trusted folders are stored home-relative and travel with a delegated run; each guest validates them against its own home (no `..`, no links out, no sensitive or startup roots) and the bridge never carries absolute paths. The `default` profile starts with `~`, which the macOS sandbox renders as write-in-home with `file-write-unlink` denied (deletes and renames, including atomic replace), sensitive and startup roots denied, and run roots re-allowed with an explicit unlink allow, because a narrower deny beats a later broad allow. Script writes in home get no Trash copy, so deletes stay with `trash_path`. The Web picker lists folders through `GET /v1/folders`, since browsers never reveal a chosen folder's path.
- 2026-10-09: Biome enforces mechanical rules because typescript-eslint cannot use the TypeScript 7 native compiler; route bodies moved out of `MarifoldService` into route modules.
- 2026-10-26: Projects (docs/projects.md) live in `core/src/projects` beside the sessions they hold, as marifold tables in the sessions database; Priest's `sessions.profile_name` is unchanged, so Priest needs no project concept. A shared `agent/Mentions` parser replaces the device-only regex.
- 2026-10-26: the context budget follows the model (`max_context_tokens = "auto"`, windows from provider listings, 128K otherwise), reversing the small fixed 16000 default; `compact_at_percent` (default 90) sets where both modes compact. Agent sessions get the same `__compaction` running summary chat uses, generated by `runtime/AgentCompaction` and written through `sessions/SessionCompaction` to the metadata column only. Priest's `compact()` deletes and reinserts every turn row, so neither background compaction nor `/compact` uses it: a turn saved meanwhile would be lost. Agent compaction runs inline at the end of a run (after the turn is saved, before `done`) and reports through a `compaction` AgentEvent, so clients show it as it happens.
